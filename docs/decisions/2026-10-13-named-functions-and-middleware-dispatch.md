# 决策：具名函数与中间件 dispatch（禁止用匿名闭包藏流程）

状态：已接受
日期：2026-10-13

背景：「包一层」这个动作在代码里没有名字——全藏在给 handler 重新赋值里。本仓最典型的是
`runWithMiddleware`：循环里 `handler = (nextSignal) => current(info, next, nextSignal)` 层层替换，
读者无法指出哪一行在进入下一层、哪一行在开始执行。同类形态还有多行闭包直接赋给字段、高阶函数工厂
里藏流程、写得不明显的递归嵌套。Koa 的 `dispatch(index)` 是同一件事的另一种写法，差别只在能不能
顺着读。

实测规模（正则加括号配对的近似值，嵌套箭头会被外层吃掉因此只会更多）：体 ≥2 行的块体箭头函数，本仓
43 处；产品仓 backend 76、frontend 121、design-system 47。而真正的「赋值型藏流程」两仓合计仅 2 处。

选项：

- (a) 只做评审约定，不写机械门禁：成本最低，但这类写法会随新步骤悄悄长回来。
- (b) 按字面统一执行「多行即具名」并全量回填，容器嵌套另立条目（选定）。
- (c) 把判据收窄成「只有赋值型才算」：命中从 287 降到 2，改动最小，但规则对新代码失去约束力。
- (d) 为内联在调用点位置的回调（JSX 属性、路由注册参数）开豁免清单：等于规范第一版就给自己开 268 张
  罚单的豁免，规则容易被无视。

决策：采用 (b)。

1. 通用规范新增「函数与流程可读性」章节：流程要能顺着读；箭头函数只在**同时**满足三条时使用
   （函数体只有一行、只使用一眼能看懂的外部变量、不承担流程控制）；多行 / 以后才调用并记住外部变量 /
   递归与中间件与重试与取消 / 回调里还有 `if`、循环或回调——一律具名。
2. 容器回调不套两层：`map` / `filter` / `some` / `find` 内再嵌容器调用时抽具名判断函数或改用 `for`。
   这条只写规范，不做机械门禁，存量不回填。
3. 中间件写具名 `dispatch(index, signal)`，下一跳放进有名字的 `runNext`；层与层之间的跳转必须有一行
   代码看得见。
4. 「先放进具名局部变量再传」的字段阈值从 6 统一到 4。

理由：本仓主要矛盾是「规则能不能被执行」，而不是「规则够不够细」。判据取「多行」而不是「是不是藏
流程」，是为了让它可机械检查、可被记住；(c) 的精确判据虽然改动小，但会让规则对新代码失去约束力——
而这类写法正是随新步骤长回来的。

后果：

- 存量回填：本仓 43 处；产品仓 backend 76 / frontend 121 / design-system 47。
- 通用规范抽出为跨仓共享件 `docs/standards/typescript-common-conventions.md`，与产品仓逐字相同，由
  `scripts/check-common-conventions.sh` 校验。改规则走「本仓提交 → 产品仓 bump `runtime.lock` 时
  因逐字比对失败而强制同步」，不再靠人记得改两边。
- 本仓加正反例夹具（`testdata/architecture/`），把「循环内把局部函数变量重新赋值为闭包」纳入机械门禁。
- 内联在调用点位置的**单行**回调不受影响（如 `onChange={(e) => setValue(e.target.value)}`）。
- 容器嵌套的存量不回填，新代码遵守。
