# red-bean-qing-tuan 开发工作流

本 Skill 是跨客户端的工作流入口，不是规范副本。`AGENTS.md` 是唯一事实来源；不得把其中的架构、编码、测试或交付规则复制到本文件。

## 开始任务

1. 用 `git rev-parse --show-toplevel` 确认当前仓库根目录，不依赖固定绝对路径。
2. 完整读取仓库根目录的 `AGENTS.md`。
3. 按 `AGENTS.md` 的路由读取当前任务直接需要的规范、契约或设计文档，不预先加载无关内容。
4. 检查工作区状态并保留用户已有改动；范围或权限不明确时先确认。
5. 根据已加载的规范判断任务是否影响公开 API、兼容性、安全边界或跨模块结构，并在需要时先取得用户决策。

如果当前工作目录不在目标仓库内，先定位用户指定的仓库；不能因此假定仓库中的 `AGENTS.md` 已被客户端自动加载。

## 执行任务

- 严格执行已加载 `AGENTS.md` 中的开发流程、模块边界、测试和交付规则。
- 编写行为实现前先确定测试层级与验收条件；适用 TDD 时先运行失败测试并确认它因目标行为缺失而失败。符合规范中的豁免场景时，记录原因和替代验证。
- 先确定改动的公开契约、实现层与消费方，保持宿主能力和 Runtime SDK 边界清晰。
- 只做用户授权范围内的修改。提交、推送、发布或修改消费方仓库仍需已有授权。

## 文档影响审查

执行 `AGENTS.md` 中的“文档影响门禁”，从 `docs/README.md` 路由到与本次 diff 有关的权威活文档。
不要在 Skill 中维护第二份“改动类型 → 文档”映射，也不要用修改冻结记录代替同步当前事实。
每一类相关文档都必须得出“已更新”或“无需更新”的结论。

## 验证与交付

1. 先运行 `make docs-check` 和与改动直接相关的定向测试，再运行 `AGENTS.md` 指定的最终交付门禁。`docs-check` 通过不能替代上面的语义审查。
2. 确认 `git diff --check` 通过，并复查最终文件清单没有遗漏文档或混入无关改动。
3. 仅在用户已授权时提交、推送或发布；完成后核对实际 revision 和目标仓库状态。
4. 最终报告实现结果、测试先行证据（先失败后通过，或豁免理由）、公开兼容性、验证结果、提交及同步状态。单列“文档影响”，逐项写明 `docs/README.md` 及其相关链接目标、`AGENTS.md`、项目 README 和设计/契约/迁移文档是“已更新”还是“无需更新（理由）”。
